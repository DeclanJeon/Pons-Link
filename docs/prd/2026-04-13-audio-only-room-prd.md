# PRD: 오디오 전용 방(1:1 / N:N) + 합의 기반 화상방 전환

작성일: 2026-04-13

## 1. 배경
현재 프로젝트는 방 타입이 사실상 화상 중심으로 설계되어 있다.
- 현재 RoomType은 'one-to-one' / 'video-group' 2종만 존재한다.
- Lobby 초기화 시 camera + microphone 권한을 함께 요청한다.
- Lobby, Room, ControlBar, Settings 전반에 카메라 토글/카메라 선택/비디오 관련 UI가 기본 노출된다.
- 비디오가 꺼진 상태에서는 참여자 프로필이 아니라 닉네임 첫 글자 fallback만 사용한다.

새 요구는 다음과 같다.
- 1:1, N:N 모두 오디오 전용 방을 지원해야 한다.
- 오디오 방에서는 프론트 카메라가 켜지면 안 된다.
- 단, 화면공유 등 카메라 외 기능은 계속 쓸 수 있어야 한다.
- Lobby에서는 음성 테스트만 가능해야 하고, 화상 테스트는 불가해야 한다.
- 네비게이션/설정/기타 UI 어디에서도 카메라 기능이 보이면 안 된다.
- 다만 참여자 전원의 동의가 있으면 같은 멤버 구성으로 화상 방으로 이동할 수 있어야 한다.
- 오디오 방에서는 서로를 영상 대신 프로필 아바타로 인식해야 하며, DiceBear 기반 아바타를 Lobby에서 직접 고를 수 있어야 한다.

즉, 본 기능의 핵심은 단순히 "비디오를 꺼 둔 방"이 아니라, 제품적으로 카메라를 숨기고 금지한 오디오 퍼스트 룸 모드를 별도 정의하는 것이다.

## 2. 문제 정의
현재 구조는 "카메라가 항상 있는 회의"를 전제로 한다. 이 구조를 그대로 두고 비디오 track만 꺼 버리면 아래 문제가 남는다.
- 사용자는 여전히 카메라 버튼/카메라 설정/카메라 테스트를 보게 된다.
- Lobby 진입 시 카메라 권한 요청이 발생할 수 있다.
- 화면공유 설정에 camera inclusion 옵션이 그대로 노출된다.
- 참여자 인식 수단이 빈약해 오디오 방 정체성이 약하다.
- 오디오 → 화상 전환이 임시 합의가 아니라 수동 재입장 수준이 된다.

따라서 제품 정책, UX, 상태 모델, 권한 요청, 전환 흐름을 함께 재설계해야 한다.

## 3. 목표
### 3.1 제품 목표
1. 사용자가 1:1 또는 그룹 통화를 오디오 전용 모드로 자연스럽게 생성/참여할 수 있다.
2. 오디오 방에서는 카메라 관련 기능이 제품 표면에서 완전히 숨겨진다.
3. Lobby에서 마이크 점검은 가능하지만 비디오 점검은 불가능하다.
4. 오디오 방에서도 화면공유, 채팅, 화이트보드, CoWatch, PonsCast 등 카메라 외 기능은 기존처럼 유지된다.
5. 오디오 방 참여자들은 영상 대신 개별 아바타로 서로를 구분한다.
6. 참여자 전원 동의 시 같은 인원과 같은 방 이름 계보를 유지하면서 화상 방으로 이동할 수 있다.

### 3.2 비즈니스/사용자 가치
- 카메라 피로감이 큰 사용자에게 진입 장벽이 낮다.
- 익명성/프라이버시 요구가 높은 통화 시나리오에 적합하다.
- 기존 화상 중심 제품을 오디오 퍼스트 협업툴로 확장할 수 있다.

## 4. 비목표
다음은 이번 PRD 범위에 포함하지 않는다.
1. 음성 전용 별도 백엔드 아키텍처 분리
2. 아바타 업로드 기능(사용자 커스텀 이미지 업로드)
3. 아바타 편집기 자체 구현
4. 부분 동의(예: 4명 중 3명만 화상 전환) 지원
5. 오디오 방 내부에서 특정 사용자만 카메라 예외 허용
6. 영상방 전환 후 개별 사용자별 비디오 강제 온 처리
7. 대규모 방송형 Stage/Spaces 모델

## 5. 대상 사용자 / 시나리오
### 5.1 주요 사용자
- 카메라 없이 대화하고 싶은 1:1 사용자
- 소규모 그룹 오디오 미팅 사용자
- 필요할 때만 합의 후 화상으로 전환하고 싶은 협업 사용자

### 5.2 핵심 시나리오
1. 사용자가 Landing에서 "1:1 오디오" 또는 "그룹 오디오"를 고른다.
2. 사용자는 방 제목과 닉네임을 입력하고 Lobby로 이동한다.
3. Lobby에서는 마이크 on/off, 마이크 선택, 입력 레벨 확인, 아바타 선택만 가능하다.
4. 카메라 미리보기/카메라 토글/카메라 선택은 없다.
5. Room 진입 후 참여자는 각자의 아바타와 닉네임으로 보이며 음성 통화한다.
6. 필요한 경우 누군가 "화상 방으로 전환 요청"을 보낸다.
7. 현재 방 참여자 전원이 동의하면 새 화상 방이 생성되고, 같은 멤버가 이동한다.
8. 새 방 이름은 원래 방 제목을 계승하되 충돌 시 #1, #2 식으로 부제가 붙는다.

## 6. 현재 코드 기준 제품 제약 및 가정
코드베이스를 읽은 결과, 다음 제약을 전제로 PRD를 정의한다.

1. 현재 방 타입
- src/types/room.types.ts 기준 현재 타입은 'one-to-one'(2인), 'video-group'(4인) 뿐이다.
- 현재 제품 정책은 1:1 오디오 2인, 그룹 오디오 8인, 그룹 화상 4인으로 분리한다.
- 단, 현재 mesh WebRTC 구조에서는 모바일 오디오 그룹은 8명까지 허용하되, 사용자 안내상 6명 이하를 권장한다.
- 만약 진짜 의미의 N:N 무제한 또는 더 높은 안정성을 원하면 signaling/server 뿐 아니라 SFU 구조 전환이 필요하다.

2. 미디어 초기화 방식
- src/services/deviceManager.ts 는 initialize()에서 getUserMedia({ audio: true, video: true })를 먼저 시도한다.
- 이 구조는 오디오 방 요구와 충돌한다. 오디오 방은 audio-only 권한 요청/초기화 경로가 별도로 필요하다.

3. UI 노출 구조
- Lobby, ControlBar, Settings, DeviceSelector, MobileCameraToggle, VideoPreview 등이 비디오 전제를 깔고 있다.
- 따라서 기능 추가보다 "room capability 기반 분기"가 먼저 필요하다.

4. 참여자 표시 구조
- 현재 VideoPreview는 비디오가 없으면 닉네임 첫 글자 fallback만 보여준다.
- 오디오방용 아바타 표시 컴포넌트/데이터 모델이 새로 필요하다.

5. 서버 연동
- signaling connect 시 roomType이 join-room payload로 전달된다.
- 오디오→화상 전환 합의/새 방 생성/충돌 이름 해결은 signaling protocol 확장이 필요하다.

## 7. 제품 요구사항

### 7.1 방 타입
시스템은 최소 4개의 사용자 인지 방 타입을 지원해야 한다.
- 1:1 화상 방
- 그룹 화상 방
- 1:1 오디오 방
- 그룹 오디오 방

권장 내부 타입 예시
- video-one-to-one
- video-group
- audio-one-to-one
- audio-group

단, 실제 네이밍은 구현 시 프로젝트 컨벤션에 맞게 정리한다.

### 7.2 Landing 요구사항
1. 사용자는 Landing에서 오디오 방과 화상 방을 명확히 구분해 선택할 수 있어야 한다.
2. 오디오 방 카드에는 "카메라 없음" 특성이 명확히 표현되어야 한다.
3. 현재 roomType URL 동기화 구조를 유지하되 오디오 타입까지 포함해야 한다.
4. 기존 화상 방 진입 플로우와 충돌 없이 공존해야 한다.

### 7.3 Lobby 요구사항
1. 오디오 방 Lobby에서는 카메라 미리보기가 보이면 안 된다.
2. 오디오 방 Lobby에서는 마이크 테스트가 가능해야 한다.
3. 마이크 테스트는 아래 중 최소 하나를 포함해야 한다.
- 마이크 mute/unmute
- 입력 레벨 시각화
- 마이크 장치 선택
4. 카메라 테스트는 할 수 없어야 한다.
5. 카메라 권한을 요청하지 않아야 한다. 단, 브라우저/OS 특성상 기존 권한이 이미 허용된 상태는 예외로 보일 수 있으나, 제품이 새로운 카메라 요청을 유도하면 안 된다.
6. 오디오 방 Lobby에서는 DiceBear 아바타 선택 UI가 제공되어야 한다.
7. 사용자는 준비된 약 50개의 아바타 중 하나를 직접 선택할 수 있어야 한다.
8. 선택한 아바타는 Room 입장 시 동일하게 유지되어야 하며, 재입장/새로고침 시에도 복원되는 것이 바람직하다.

### 7.4 오디오 방 Room 요구사항
1. 오디오 방에서는 참여자가 영상 대신 아바타와 닉네임으로 표현되어야 한다.
2. 로컬 사용자도 동일하게 아바타 기반으로 표현되어야 한다.
3. 말하는 사람 강조(speaking state), mute 상태, 화면공유 상태는 아바타 타일/카드 위에서 식별 가능해야 한다.
4. 카메라 on/off 버튼은 보이면 안 된다.
5. 모바일의 카메라 전환 버튼도 보이면 안 된다.
6. 설정 패널에서 카메라 장치 선택, 비디오 설정, 화면공유에 카메라 포함 옵션이 보이면 안 된다.
7. 오디오 방에서도 아래 기능은 계속 사용할 수 있어야 한다.
- 화면공유
- 채팅
- 화이트보드
- CoWatch
- PonsCast / 파일 스트리밍
- 릴레이 등 기존 카메라 외 기능

### 7.5 화면공유 정책
1. 오디오 방에서도 화면공유는 허용된다.
2. 단, 화면공유에 카메라를 PIP로 합성하는 기능은 오디오 방에서 비활성화되어야 한다.
3. 즉 "화면공유는 가능, 카메라 동반 화면공유는 불가"가 정책이다.

### 7.6 네비게이션/설정 가시성 요구사항
오디오 방에서 아래 항목은 사용자에게 노출되면 안 된다.
- 카메라 토글 버튼
- 카메라 시작/종료 텍스트
- 카메라 전환 버튼
- 카메라 선택 드롭다운
- Video Settings 섹션
- 화면공유 시 카메라 포함 스위치
- 카메라 권한 안내 문구
- 비디오 관련 네비게이션 아이콘/툴팁/shortcut 문구

이 요구는 "disabled 상태로 보이기"가 아니라 "UI 비노출"이 원칙이다.

### 7.7 합의 기반 화상 방 전환
1. 오디오 방에서 어떤 참여자든 "화상 방으로 전환 요청"을 시작할 수 있다.
2. 요청이 시작되면 현재 방의 활성 참여자 전원에게 동의 UI가 보여야 한다.
3. 전원 동의가 모일 때만 전환이 성립한다.
4. 한 명이라도 거절하거나 시간 초과되면 전환은 취소된다.
5. 전환이 성립하면 현재 참여자만 대상으로 새 화상 방을 생성하고 함께 이동한다.
6. 새 방 이름은 기존 방 이름을 우선 사용한다.
7. 이미 동일한 이름의 방이 존재하면 "원래이름 #1", "원래이름 #2" 식으로 suffix를 붙인다.
8. 이동 후 닉네임, 참여자 구성, 아바타 선택 상태는 유지되는 것이 바람직하다.
9. 이동 후에는 화상 방 정책을 따르므로 카메라 UI가 다시 활성화될 수 있다.
10. 전환 요청/동의/거절/만료는 참여자 모두에게 명확한 상태 메시지로 보여야 한다.

### 7.8 아바타 요구사항
1. DiceBear HTTP API를 사용해 약 50개의 기본 아바타 후보를 제공한다.
2. MVP에서는 seed 기반 URL 세트 사전 생성 방식이면 충분하다.
3. 아바타 목록은 Lobby에서 선택 가능해야 한다.
4. 선택한 아바타는 로컬 상태와 세션/스토리지에 저장되어야 한다.
5. Room 참가 시 peer metadata 또는 signaling payload를 통해 다른 참여자에게 전파되어야 한다.
6. 네트워크 실패 또는 DiceBear 응답 실패 시 기본 fallback 아바타 세트가 있어야 한다.

## 8. 상세 UX 요구사항

### 8.1 Landing
- 오디오 모드와 화상 모드는 아이콘/문구로 명확히 구분
- 오디오 모드 설명에 "camera hidden", "voice-first" 성격 포함
- 기존 one-to-one, group 개념은 유지 가능

### 8.2 오디오 Lobby
표시
- 방 제목
- 닉네임 편집
- 아바타 선택 그리드 또는 carousel
- 마이크 미리듣기/입력 레벨
- 마이크 mute/unmute
- 마이크 장치 선택
- 입장 버튼

표시 금지
- 로컬 카메라 프리뷰
- 카메라 장치 선택
- 카메라 on/off 버튼
- 카메라 권한 유도 문구

### 8.3 오디오 Room
표시
- 참여자 아바타
- 닉네임
- 말하는 중 상태
- 음소거 상태
- 화면공유 상태
- 화상방 전환 요청 버튼(권한 제한은 추후 결정 가능)

표시 금지
- 비디오 타일 중심 레이아웃
- 카메라 관련 control
- 카메라 display/object-fit 설정
- 모바일 카메라 전환

### 8.4 화상방 전환 모달/토스트
요청자
- "화상 방으로 전환을 요청했습니다. 참여자 동의를 기다리는 중"

수신자
- "OOO님이 화상 방 전환을 요청했습니다"
- 동의 / 거절
- 제한 시간 표시

결과
- 성공: "전원 동의 완료. 화상 방으로 이동합니다"
- 실패: "전환이 취소되었습니다. 일부 참여자가 동의하지 않았습니다" 또는 "응답 시간이 만료되었습니다"

## 9. 데이터/상태 요구사항
최소 상태 필드 예시
- roomType
- roomCapabilities: { audio: true, camera: false, screenShare: true, cameraInScreenShare: false, avatarRequired: true }
- avatarId 또는 avatarUrl
- upgradeRequest: { requesterId, requestedAt, expiresAt, approvals, rejections, status }
- migratedRoomTitle
- migratedFromRoomId

스토리지 권장
- nickname: 기존 sessionManager 유지 가능
- avatar selection: localStorage 또는 sessionStorage 유지
- roomType: URL query + session state 동기화

## 10. 성공 지표
정량 지표 예시
1. 오디오 방 Lobby 진입 시 카메라 권한 요청 발생률 0에 수렴
2. 오디오 방에서 카메라 관련 UI 노출 버그 0건
3. 오디오 방 Lobby → Room 진입 성공률이 기존 화상방 대비 유사 수준 유지
4. 화상방 전환 합의 플로우 완료율 추적 가능
5. 아바타 선택 완료율 및 기본값 사용률 추적 가능

정성 지표
- 사용자가 "카메라가 없는 통화 모드"라고 즉시 이해할 수 있어야 함
- 화면공유 허용과 카메라 금지 정책이 혼란 없이 전달되어야 함

## 11. 수용 기준
### AC-01 방 타입 선택
- Landing에서 1:1 오디오 / 그룹 오디오를 선택할 수 있다.
- URL과 내부 상태가 동기화된다.

### AC-02 Lobby 카메라 비노출
- 오디오 방 Lobby에서 비디오 프리뷰가 보이지 않는다.
- 카메라 on/off 버튼이 없다.
- 카메라 장치 선택이 없다.

### AC-03 Lobby 음성 테스트 가능
- 오디오 방 Lobby에서 마이크 mute/unmute 및 음성 테스트가 가능하다.
- 최소 한 개 이상의 마이크 입력 상태 피드백이 있다.

### AC-04 카메라 권한 차단
- 오디오 방 Lobby/Room 진입 과정에서 앱이 카메라 getUserMedia를 요청하지 않는다.

### AC-05 Room 카메라 UI 비노출
- 오디오 방 Room의 ControlBar/Settings/모바일 UI 어디에도 카메라 관련 기능이 보이지 않는다.

### AC-06 화면공유 유지
- 오디오 방에서도 화면공유 시작/종료가 가능하다.
- 오디오 방에서는 화면공유에 카메라 포함 옵션이 없다.

### AC-07 아바타 표시
- 참여자는 영상 대신 선택한 아바타와 닉네임으로 표시된다.
- 선택한 아바타가 원격 참여자에게도 동일하게 보인다.

### AC-08 아바타 선택
- Lobby에서 약 50개 DiceBear 아바타 중 하나를 선택할 수 있다.

### AC-09 화상 전환 합의
- 오디오 방에서 화상 전환 요청을 보낼 수 있다.
- 전원 동의 시에만 새 화상 방으로 이동한다.
- 한 명이라도 거절/타임아웃이면 이동하지 않는다.

### AC-10 방 이름 계승
- 화상방 전환 시 원래 방 이름을 우선 계승한다.
- 중복 시 #1, #2 suffix 규칙이 적용된다.

## 12. 우선순위
### P0
- RoomType 확장
- audio-only capability 모델 도입
- Lobby audio-only UX
- audio-only media initialization (camera 금지)
- Room/ControlBar/Settings에서 camera UI 제거
- DiceBear 아바타 선택/표시

### P1
- 합의 기반 화상방 전환 플로우
- 방 이름 충돌 해결 규칙
- peer metadata로 avatar 전파
- 오디오방 전용 speaking/mute 강조 polish

### P2
- 아바타 검색/필터
- 더 넓은 DiceBear 스타일 선택
- 전환 요청 이력/재요청 쿨다운

## 13. 리스크
1. 현재 미디어 초기화가 audio+video 동시 요청 구조여서 audio-only 분리 영향이 큼
2. VideoPreview 중심 컴포넌트 구조라 avatar-first room 레이아웃 분기가 필요함
3. signaling/server에 전환 합의 프로토콜이 없으면 프론트만으로 완결 불가
4. 기존 screen share 구현은 camera overlay 옵션을 포함하므로 capability gating 누락 시 정책 위반 가능
5. room title uniqueness 검증 주체가 서버라면 suffix 부여 규칙을 서버와 함께 설계해야 함

## 14. 오픈 이슈
1. 그룹 오디오 정원을 기존 4명으로 둘지, 진짜 N:N 확장할지?
2. 화상 전환 요청 시작 권한을 누구나 가질지, host 개념을 둘지?
3. 전원 동의 기준에서 "잠수 상태/네트워크 불안정 참여자"를 어떻게 처리할지?
4. DiceBear 스타일을 하나로 고정할지, 여러 스타일을 섞을지?
5. 아바타 선택 저장 범위를 브라우저 전체 기본값으로 할지, 방별로 할지?

## 15. 권장 구현 방향 요약
1. roomType 문자열 분기보다 room capability 유틸을 먼저 만든다.
2. media initialization을 video-optional이 아니라 room policy driven으로 재구성한다.
3. Lobby/Room/Settings/ControlBar를 capability 기반 렌더링으로 바꾼다.
4. avatar participant card를 별도 컴포넌트로 도입한다.
5. signaling payload에 avatar + room upgrade proposal 상태를 추가한다.
6. 오디오→화상 전환은 기존 room leave/join을 감싼 제품 플로우로 설계한다.

## 16. 최종 정의
이 기능은 "기존 화상방에서 카메라만 끈 상태"가 아니다.
이 기능은 다음을 만족하는 별도의 제품 모드다.
- 카메라 권한 요청 금지
- 카메라 UI 비노출
- 아바타 기반 참여자 인식
- 화면공유 등 협업 기능 유지
- 전원 동의 기반 화상방 승격 지원

이 원칙이 깨지면 오디오 전용 방 기능은 제품적으로 실패한 것으로 본다.
