# Meeting Minutes Design

## Status

Draft for `feature/meeting-minutes`.

## Goal

Add a meeting minutes system that records finalized live-caption text from all connected participants into Chat, and lets users download the collected meeting records from the Chat panel.

This feature is room-scoped, not only local-user scoped. If one participant enables meeting minutes, every connected participant should contribute finalized speech captions to the shared meeting record.

## Non-goals for MVP

- No AI summarization.
- No action-item extraction.
- No PDF/DOCX export.
- No backend persistence across refresh/rejoin.
- No forced visible subtitle overlay for every participant.
- No recording of unstable interim STT results.

## Core Product Behavior

1. A user enables `Meeting Minutes` from Settings.
2. The app broadcasts a room-wide meeting-minutes state to peers.
3. Every connected participant receives the state.
4. While meeting minutes are enabled, each participant runs local STT final-caption capture if microphone access and STT support are available.
5. Each participant emits only finalized caption records to peers.
6. Every client records local and remote finalized caption records into Chat as meeting-minute messages.
7. Chat shows meeting-minute messages in the same timeline as user chat messages, but with a clear `Minutes` marker.
8. Chat provides one action to download all meeting-minute records.

## Key UX Principle

Meeting minutes should turn on STT contribution, not necessarily visible caption overlays.

- `Live caption overlay`: whether a user sees captions on screen.
- `Meeting minutes capture`: whether finalized speech text is collected into Chat records.

These should be separate. A participant may contribute final STT to the meeting record without showing large subtitle UI on their own screen.

## Settings UX

Add a `Meeting Minutes` control near existing `Captions & Translation` settings.

Recommended copy:

- Section title: `Meeting Minutes`
- Toggle label: `Record meeting minutes for this room`
- Helper text: `When enabled, finalized live speech from connected participants is saved into Chat as meeting records.`
- Enabled status: `Meeting minutes are recording for this room.`
- Disabled status: `Meeting minutes are off.`

When enabled by any participant, all clients should show a visible room status indicator:

- `Meeting minutes recording`
- Optional detail: `Final captions are being saved to Chat.`

## Consent and Transparency

Because enabling meeting minutes makes other clients run STT contribution, the UI must clearly indicate room recording state.

MVP requirements:

- Show a non-modal status indicator when room meeting minutes are active.
- Do not silently enable a visible subtitle overlay on other users' screens.
- If local STT cannot start because microphone permission is denied, show a warning/toast locally and mark that participant as not contributing.

Future option:

- Add per-user opt-out, if privacy requirements demand it.

## Data Flow

### Room meeting state

Introduce a room-wide data-channel message:

```ts
type MeetingMinutesStateMessage = {
  type: 'meeting-minutes-state';
  payload: {
    enabled: boolean;
    ownerId: string;
    ownerNickname: string;
    startedAt?: number;
    stoppedAt?: number;
    version: 1;
  };
};
```

Behavior:

- Sender broadcasts when toggled in Settings.
- Receivers update local room meeting-minutes state.
- New peers need current state replay. The current owner should rebroadcast state when peers join, or the room orchestrator should include state in existing sync flows.

### Caption record emission

When room meeting minutes are enabled, each client emits finalized local STT results as caption records.

```ts
type MeetingMinutesCaptionMessage = {
  type: 'meeting-minutes-caption';
  payload: {
    captionId: string;
    speakerId: string;
    speakerNickname: string;
    text: string;
    lang: string;
    provider: 'azure' | 'deepgram' | 'browser';
    capturedAt: number;
    meetingStartedAt?: number;
    version: 1;
  };
};
```

`captionId` should be generated by the speaking client and must be stable enough for dedupe.

Recommended ID:

```ts
captionId = `${roomId}:${speakerId}:${capturedAt}:${hash(text)}`
```

MVP can use `nanoid()` plus dedupe fallback, but deterministic IDs are better for replay/reconnect.

### Chat record creation

Every client converts each unique `meeting-minutes-caption` into a Chat message:

```ts
type ChatMessage = {
  id: string;
  type: 'text';
  text: string;
  senderId: string;
  senderNickname: string;
  timestamp: number;
  source?: 'user' | 'meeting-minutes';
  meetingMinutes?: {
    captionId: string;
    speakerId: string;
    speakerNickname: string;
    sourceLang: string;
    provider: 'azure' | 'deepgram' | 'browser';
    capturedAt: number;
  };
};
```

Display:

- Keep the real speaker as sender.
- Add a visible `Minutes` badge.
- Add helper text such as `Recorded from live speech`.
- Disable edit/delete for meeting-minute messages unless a future edit workflow is designed.

## STT Activation Logic

Current live captions use `isTranscriptionEnabled` and are final-only in `Room.tsx`.

Meeting minutes need a derived STT requirement:

```ts
const shouldRunSpeechRecognition = isTranscriptionEnabled || meetingMinutesRoomState.enabled;
```

But output handling must branch:

- If `isTranscriptionEnabled`, update local subtitle transcript and send normal transcription payload for overlay.
- If `meetingMinutesRoomState.enabled`, emit `meeting-minutes-caption` for final results.

Do not record interim results.

Do not require `isTranscriptionEnabled` to be on for meeting-minutes contribution. Meeting minutes can run STT in the background without showing overlay captions.

## Deduplication

Deduplication is required in two places.

### STT source dedupe

Existing STT dedupe already prevents provider repeated final messages. Keep this.

### Meeting record dedupe

Chat/minutes layer should dedupe by:

1. `captionId` if present.
2. Fallback tuple: `speakerId + normalizedText + capturedAt bucket`.

Recommended fallback bucket: 2 seconds.

This prevents duplicates from:

- data-channel replay,
- reconnect,
- provider repeated finals,
- local plus remote double conversion.

## Download Design

Chat panel should expose `Download records` when at least one meeting-minute message exists.

MVP export format: Markdown.

Filename:

```txt
pons-meeting-records-YYYY-MM-DD-HHmm.md
```

Markdown structure:

```md
# Pons Meeting Records

- Room: <room id or title>
- Exported: <ISO datetime>
- Records: <count>

## Timeline

### 10:31:22 - Alice
안녕하세요.

### 10:31:45 - Bob
회의를 시작하겠습니다.
```

Future export formats:

- JSON for structured import.
- TXT for simple transcript.
- PDF/DOCX after persistence/formatting requirements are clear.

## State Ownership

### Local persisted preference

Users may keep a local preference for whether they usually want meeting minutes enabled, but the active room state must be room-wide and synchronized.

Suggested split:

```ts
meetingMinutesPreferenceEnabled: boolean; // persisted local preference, optional
meetingMinutesRoomState: {
  enabled: boolean;
  ownerId?: string;
  ownerNickname?: string;
  startedAt?: number;
}; // runtime room state
```

For MVP, Settings can directly toggle room state. Persistence of the preference is optional and should not override an active room's state unexpectedly.

## Testing Plan

### Store/unit tests

- Meeting-minutes room state toggles on/off.
- State broadcast payload is created correctly.
- Final STT emits meeting-minutes caption only when room state is enabled.
- Interim STT does not emit meeting-minutes caption.
- Duplicate caption records are ignored.
- Meeting-minute Chat messages preserve speaker, timestamp, language, provider.
- Download markdown includes only meeting-minute messages and preserves chronological order.

### Component tests

- Settings shows `Record meeting minutes for this room` toggle.
- Toggling Settings broadcasts room state.
- Chat renders meeting-minute messages with `Minutes` badge.
- Chat download button is disabled when there are no records.
- Chat download button creates a Markdown file when records exist.

### Integration tests

- One user enables meeting minutes; remote clients update active state.
- Local final STT result creates a meeting-minute Chat message.
- Remote meeting-minutes caption creates a meeting-minute Chat message.
- Live caption overlay can remain off while meeting minutes still capture final STT.
- Reconnect/replay does not duplicate records.

## Risks and Mitigations

### Risk: Privacy surprise

Turning on another participant's STT contribution can be sensitive.

Mitigation:

- Always show room recording indicator.
- Do not hide the state inside Settings only.
- Consider opt-out later.

### Risk: Chat spam

Every finalized utterance can create many Chat entries.

Mitigation for MVP:

- Keep records concise.
- Use subtle visual styling.
- Future: batch consecutive utterances by same speaker within a short window.

### Risk: Divergent room logs

If each client decides locally whether to derive minutes, logs can differ.

Mitigation:

- Use room-wide meeting state.
- Speaking client emits canonical caption record.
- All clients dedupe and insert the same record.

### Risk: Lost records after refresh

Chat is in-memory.

Mitigation:

- MVP explicitly supports current-session export only.
- Future: backend persistence keyed by room/session.

## Final MVP Recommendation

Implement room-wide meeting minutes as a synchronized room state plus canonical caption-record messages.

Do not couple this to visible subtitle overlays. Instead, meeting minutes should require STT final-caption contribution from each participant while leaving visible captions as a separate user-facing preference.

Build the MVP around:

1. Room-wide `meeting-minutes-state`.
2. Per-speaker `meeting-minutes-caption` final records.
3. Chat insertion with `source: 'meeting-minutes'` metadata.
4. Chat-level Markdown download.
5. Visible recording indicator and clear Settings copy.
